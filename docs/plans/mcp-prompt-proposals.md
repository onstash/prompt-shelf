# Plan: MCP access to prompts with versioned proposals

Status: Proposed
Decisions: [ADR-0009](../decisions/0009-mcp-server-with-oauth.md), [ADR-0010](../decisions/0010-prompt-update-proposals.md)

This is a working checklist. Delete it once the work is merged and verified. The ADRs keep the reasons and stay in the repository.

## Goal

An AI client (ChatGPT, Codex, or another MCP client) can:

- search and read the user's prompts,
- render a prompt into text for copying,
- propose an edit to a prompt.

The user approves every proposed edit in Prompt Shelf before it becomes a new version. The MCP side never approves anything.

## Non-goals

- No changes to LifeOS or Total Recall.
- No AI execution inside Prompt Shelf (ADR-0005 still applies).
- No approval through MCP, and no approval scope.
- No content-hash binding for approvals in v1. Revisit if proposals become editable or other people can approve them.
- No team sharing, roles beyond owner and admin, or billing.
- No widget or UI components for the AI client.

## Settled decisions

| Topic | Decision |
| --- | --- |
| Where it lives | Prompt Shelf repository, in the existing TanStack Start Worker |
| Authorization server | Better Auth with `jwt()` and `mcp()` plugins, same pattern as LifeOS |
| Client registration | Unauthenticated dynamic client registration allowed; consent screen always shown |
| Client ID metadata documents | To be checked: `@better-auth/cimd` exists for Better Auth 1.7.13. Not decided; DCR is the default |
| Tool surface | Two tools: `search` (discover operations) and `execute` (run one) |
| Scopes | `prompt-shelf.search`, `prompt-shelf.execute`, `prompt-shelf.propose`, `offline_access` |
| Token lifetimes | Access token about 1 hour. Refresh token 1 week, so a connected app works for a week before reconnecting |
| Approval | Browser session only, owner or admin role only |
| Versioning | Immutable revisions. Proposals are separate records. Approval is a guarded write that checks `base_version` |
| Content-hash binding | Not in v1 (see ADR-0010) |

## Progress (2026-11-17)

Done and verified locally (not committed):

- Better Auth set to 1.7.25 with `@better-auth/mcp` and `@better-auth/drizzle-adapter`. 1.7.13 was tried first and failed: `@better-auth/mcp` needs `@better-auth/core` 1.7.25, while `better-auth` 1.7.13 pulls in core 1.7.13.
- `jwt()` and `mcp()` added to `createAuth`, with dynamic registration (DCR) enabled and unauthenticated registration allowed.
- Migration `0005_oauth_provider.sql` applied to local D1. Tables match the Drizzle definitions generated by the Better Auth schema generator.
- Discovery routes serve protected-resource metadata and authorization-server metadata (checked with curl).
- DCR checked: an unauthenticated client registration returns HTTP 201 with a client ID. The test client was removed from the local database afterward.

Blocked or open:

- **CIMD is blocked.** The `@better-auth/cimd` fetcher for Node uses `node:dns` and `node:https`. The package requires DNS resolve-once with connection pinning, and the Worker `fetch` API does not appear to offer that. Needs a decision before anything is wired up.
- **MCP transport decision.** `@better-auth/mcp` 1.7.13 documents `@modelcontextprotocol/server` v2 for MCP 2026-07-28, with `legacy: "reject"`. Total Recall uses `@modelcontextprotocol/sdk` 1.32.2. Older clients may need the legacy transport.
- `/consent` and `/sign-in` UI are not built yet, so the browser authorization flow cannot complete.
- `/mcp` endpoint not built (Phase 4).

## Risks

- **Worker compatibility.** Total Recall runs the same SDK transport on Workers, which lowers the risk. Still verify here.
- **Consent screen spoofing.** The consent screen must show the client name and requested scopes clearly.
- **Leaked refresh token.** A leaked refresh token works for up to a week. Revocation from the connected-apps screen must work immediately.
- **Rate limits.** Not yet set. Needed on `propose_update` at minimum.
